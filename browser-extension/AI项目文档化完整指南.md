项目信息：
- 项目名称：[项目名]
- 项目类型：[Web应用/桌面应用/库/工具等]
- 主要技术栈：[技术列表]
- 项目路径：[绝对路径]
请执行以下任务：
1. 扫描项目结构
- 列出所有主要目录和文件
- 识别核心代码、配置文件、文档
- 发现临时文件、测试文件、构建产物
2. 分析项目组成
- 前端/后端/数据库架构
- 关键依赖和配置
- 构建和部署流程
- 现有文档情况
3. 生成初步报告
   创建文档：project_analysis.md

- 项目概览

- 需要整理的问题清单
完成后告诉我，我会给你下一阶段的指示。

阶段2：文件整理与归档
【项目文档化 - 第2阶段：文件整理】
基于你的分析报告，现在进行文件整理。
请执行以下操作：
1. 创建标准目录结构
   建议创建（如果不存在）：
- .internal/           # 内部文档（不提交Git）
- .internal/knowledge-base/  # 知识库
- .internal/archive/         # 历史归档
- .internal/planning/        # 项目规划
- scripts/             # 工具脚本
- docs/                # 用户文档
2. 识别需要移动的文件
- 临时文件 → .internal/temp/
- 旧版本代码 → .internal/archive/
- AI对话记录 → .internal/ai-assistance/
- 构建日志 → .internal/archive/build-logs/
3. 清理建议
   列出可以删除的文件（不要直接删除）：
- node_modules（已在.gitignore）
- 重复的备份文件
- 临时测试文件
- 过时的配置文件
4. 更新.gitignore
   确保包含：
- .internal/（如果是私有知识）
- 构建产物
- IDE配置
- 系统文件
生成文档：file_organization_plan.md
包含具体的文件移动方案，等待我确认后再执行。

阶段3：核心文档生成
【项目文档化 - 第3阶段：核心文档】
现在创建项目的核心文档。
1. README.md（用户视角）
   必须包含：
- 项目简介（1-2句话）
- 功能特性（列表）
- 安装步骤（详细）
- 快速开始（5分钟上手）
- 常见问题FAQ
- 截图/演示（如适用）
- 许可证信息
- 贡献指南链接
   风格要求：
- 清晰易懂
- 配置徽章（版本、许可证等）
- Markdown格式优美
- 包含目录
2. PROJECT_OVERVIEW.md（开发者视角）
   必须包含：
- 项目定位与目标
- 完整技术架构（含架构图）
- 目录结构详解
- 开发流程（本地开发→构建→部署）
- 技术决策记录
- 已知问题与解决方案
- 未来规划
3. CONTRIBUTING.md（贡献指南）
   包含：
- 如何提交问题
- 代码规范
- Pull Request流程
- 本地开发环境搭建
4. CHANGELOG.md（如果有多个版本）
- 按版本记录变更
- 遵循Keep a Changelog格式
请逐个创建这些文档，每个文档创建后暂停，等我确认。

💡 最佳实践
1. 分阶段执行
不要一次性要求所有文档，分5个阶段：
1. 分析（了解现状）
2. 整理（清理归档）
3. 核心文档（基础文档）
4. 知识库（深度总结）
5. 报告（全面回顾）
每个阶段完成后确认质量再进行下一阶段。
2. 提供充分上下文
好的prompt包含：
- 项目名称和类型
- 项目路径
- 主要技术栈
- 特殊要求
- 期望的文档风格
不好的prompt：
"帮我整理这个项目"
3. 迭代优化
- 第一遍生成后，审阅并提出修改
- 指出具体问题："这个章节太简略，需要添加..."
- 要求补充细节："请展开说明XX的实现过程"
4. 保持一致性
建立文档模板：
在第一个项目中，让AI生成文档模板：
"基于这次的文档经验，生成一套可复用的文档模板"
后续项目直接使用：
"按照[模板路径]的格式，生成本项目的XX文档"
5. 版本控制文档
文档也需要版本管理：
- 文档头部标注版本和日期
- 重大修改记录在CHANGELOG
- 归档旧版本到.internal/archive/
